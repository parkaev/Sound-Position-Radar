# Sound Position Radar — архитектура (v0.3, 360° через многоканальный захват)

Визуальный индикатор направления звука для игр: показывает на экране, с какой стороны
звучат громкие звуки. Инструмент доступности. Windows-only.

## 1. Принципы

1. **Не чит.** Мы не читаем память игры, не внедряемся в процесс, не эмулируем ввод. Мы слушаем
   ровно тот звук, который игрок и так слышит через колонки/наушники, и показываем его
   пространственно. Это parity-доступность: информация, которую человек с двумя рабочими ушами
   получает естественно (аналог цветовых фильтров для дальтоников).
2. **Только публичные API ОС.** Захват звука уровня OBS / Discord — та же поверхность API.
3. **Низкая латентность.** Цель «звук → пиксель» < 60–80 мс, иначе подсказка бесполезна.
4. **Работает поверх любой игры** без per-game интеграции (профили — только для тонкой настройки).

## 2. Физическая основа и честные ограничения

Игра рендерит 3D-звук в стерео: источник справа → громче в правом канале. Мы восстанавливаем
азимут из межканальной разницы уровней (ILD — interaural level difference).

Что стерео-баланс **не** даёт (принимаем заранее, пишем в документации для пользователей):

| Ограничение | Следствие / мера |
|---|---|
| Стерео-микс (2 канала) не различает «перед/зад» и «выше/ниже» | Индикатор 180° + затемнённый задний сектор. **360° — опция (чекбокс, по умолчанию выкл.)**: если игра рендерит 5.1/7.1, захватываем многоканальный микс ДО даунмикса в стерео, направление — векторная сумма энергий по углам динамиков (ChannelMap). Извлечение перед/зад из HRTF-стерео — исследовательская задача (M3+) |
| Два одновременных источника дают «центроид» | Частично лечится анализом по частотным полосам (бас-взрыв + вч-шаги = 2 маркера); полноценная мульти-источность — M3 |
| HRTF-виртуализация (Windows Sonic / Dolby Atmos for Headphones) искажает зависимость ILD↔угол | Рекомендуем обычное стерео; для HRTF-игр — таблица калибровки (M3) |
| Компрессия и громкая музыка в играх | Адаптивный фоновый порог по полосам (см. 3.2) |
| Фоновые колебания замороженного фона (±3–5 дБ/блок) перетягивали азимут к центроиду каналов | Направление обновляется только на блоках с громкостью уровня онсета (найдено при отладке 360°) |

## 3. Высокоуровневая схема

```
[Игра] ──WASAPI──▶ [IAudioSource] ──▶ [RingBuffer] ──▶ [Analyzer / DSP] ──SoundEvent──▶ [EventHub] ──▶ [UI]
                  (поток захвата)                    (фоновый поток, блоки 21 мс)     (Channel)   (тест-окно → потом оверлей)
```

Захват выдаёт пачки ~10 мс → кольцевой буфер → поток анализа считает блоки 1024 отсчётов
(≈21 мс @ 48 кГц) → события уходят в UI через `System.Threading.Channels`.

## 4. Компоненты

### 4.1 Захват звука — `IAudioSource`

Два источника за одним интерфейсом, переключаются в UI:

- **`ProcessLoopbackSource` (основной).** `ActivateAudioInterfaceAsync` с
  `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK` — ОС отдаёт нам микс **конкретного процесса**
  (опционально с дочерними). Мы не открываем хэндлы процесса и не трогаем его — тот же механизм,
  что у OBS «Application Audio Capture» (public API, Windows 10 build 20348+ / Windows 11;
  текущая ОС — новый Win11, API доступен). Запрашиваем формат IEEE float32, 48 кГц, стерео —
  ОС сама сводит к нему микс процесса.
- **`DeviceLoopbackSource` (фолбэк + отладка).** Весь выход устройства по умолчанию
  (NAudio `WasapiLoopbackCapture`, почти одна строка). Нужен для старых Win10 и когда
  процесс-пикер не находит игру (лаунчеры-обёртки типа Riot Client запускают игру дочерним
  процессом — надо брать PID именно игры, режим `INCLUDE_TARGET_PROCESS_TREE` это покрывает).

**Выбор процесса:** список процессов, которые сейчас воспроизводят звук (перечисление аудио-сессий
устройства через `IAudioSessionManager2` — публичный API), + ручной ввод имени exe/PID.

### 4.2 DSP-конвейер — `Analyzer`

На каждый блок 1024 отсчётов:

1. Окно Ханна → FFT-1024 (MathNet.Numerics; при нежелании зависимости — свой radix-2, ~30 строк).
2. Энергия по **5 полосам** и по каналам L/R:
   `<150 | 150–500 | 500–2k | 2–6k | >6k` Гц. (Шаги живут в 150–2к, выстрелы широкополосны,
   бас музыки — ниже 150: маскирование музыки по полосам получается бесплатно.)
3. **Адаптивный фон:** на каждую полосу — трекер фона (EMA перцентиля ~P80, окно 2–5 с).
   Фиксированный порог в играх не работает из-за компрессии и музыки.
4. **Детекция онсета:** энергия полосы выше `фон + N дБ` (N настраивается, стартово 8–10 дБ)
   ≥ 2 блока подряд → onset. Соседние блоки склеиваются в событие (гэп < 150 мс), событие
   закрывается, когда энергия падает ниже `фон + 4 дБ` на > 300 мс.
5. **Азимут** (constant-power pan law):
   `θ = 90° · ( (4/π)·atan2(√E_R, √E_L) − 1 )`, где E — энергия, взвешенная по полосам события
   (вес = превышение над фоном: самый громкий компонент события тянет угол на себя, бас музыки
   не смазывает). Полином сглаживания угла внутри события по SNR.
6. **Выход:** `SoundEvent { Id, T0, T1, Azimuth°, Salience dB, BandProfile[5], Confidence }`.

Хук калибровки: таблица ILD↔угол может подменяться профилем игры (для HRTF-миксов).

### 4.3 Шина событий — `EventHub`

- `Channel<SoundEvent>` из потока анализа в UI-поток;
- журнал сессии JSONL (`%APPDATA%/SoundPositionRadar/logs/…`) — для отладки, реплеев и
  автотестов по логу;
- будущие потребители: оверлей, звуковые/вибро-уведомления.

Поведение «предварительная метка»: wedge показывается сразу по первому онсету (~40–60 мс),
угол уточняется по мере события — иначе теряем латентность на ожидании стабилизации.

### 4.4 UI MVP — тест-окно (WPF)

- Холст: дуга 180° (сразу в том виде, как будет выглядеть оверлей), сектор-указатель:
  угол = азимут, цвет/размер = громкость, затухание ~1 с;
- живые метры: L/R энергия и фон/порог по полосам — видно, «что думает» детектор;
- список событий (время, угол, дБ);
- слайдеры: порог над фоном, сглаживание, мин. громкость;
- выбор источника (процесс / всё устройство) и процесса; вкл/выкл записи JSONL.

Оверлей в MVP не делаем — только это окно.

### 4.5 Будущий оверлей (M2)

- Отдельное topmost-прозрачное окно, click-through (`WS_EX_TRANSPARENT | WS_EX_NOACTIVATE`),
  без инъекций в рендер игры;
- требование: игра в borderless windowed (в exclusive fullscreen оверлей не виден);
- позиция/размер/прозрачность настраиваются; горячая клавиша вкл/выкл; иконка в трее.

## 5. Технологии (уточнено при реализации)

- **.NET 10 (LTS) / C#**, WPF — тест-окно и будущий оверлей (Windows-only тул, осознанно).
- **NAudio 3.3.0** — начиная с 3.0 process loopback capture встроен
  (`WasapiRecorderBuilder.WithProcessLoopback(pid, mode).BuildAsync()`), ручной COM-interop
  (`ActivateAudioInterfaceAsync` + `IActivateAudioInterfaceCompletionHandler`) не понадобился.
  Device loopback — `WithLoopbackCapture()`. Для перечисления аудио-сессий (процесс-пикер)
  написан компактный interop `IAudioSessionManager2`.
- FFT — собственный radix-2 (~70 строк); MathNet не нужен. xUnit для тестов.
- Дистрибуция: single-file self-contained exe, без установщика.

## 6. Структура репозитория

```
src/
  SoundRadar.Core/          # без UI: захват, DSP, события, конфиг
    Audio/   IAudioSource, ProcessLoopbackSource, DeviceLoopbackSource, AudioProcessPicker
    Dsp/     Analyzer, BandSplitter, BackgroundTracker, OnsetDetector, PanMath
    Events/  SoundEvent, EventHub, JsonlLogger
  SoundRadar.App/           # WPF-тест-окно (MVP)
  SoundRadar.Emitter/       # тестовая утилита: играет панорамированные звуки по расписанию
tests/
  SoundRadar.Core.Tests/
docs/ARCHITECTURE.md
```

`SoundRadar.Emitter` — генератор тестовых сцен (клики/«шаги»/«выстрелы» на заданных углах по
расписанию): регресс-тест детектора без запуска игры.

## 7. Тестирование

- **Юнит (синтетика):** источник на пан-позиции P → ожидаемый угол ±3°; фон + онсет → событие;
  тихо → нет события; музыка-фон + шаги поверх → событие не теряется.
- **Интеграция:** Emitter проигрывает последовательность −90/−45/0/45/90° → JSONL-лог содержит
  события с этими углами (автотест читает лог).
- **Ручной приём:** CS2 deathmatch: шаги слева/справа/сзади, лог vs реальность.

## 8. Риски

| Риск | Мера |
|---|---|
| **Win11 25H2 (build 26200+) — регрессия: `ActivateCompleted` не приходит никогда** | Таймаут активации 8 c → ясная ошибка; пользователь переключается на DeviceLoopback (реализовано). Проверить на свежих сборках |
| Process loopback недоступен (старые Win10 < 19041) | Фолбэк на DeviceLoopback; проверка версии ОС при старте |
| Игра/лаунчер разбивает аудио по дочерним процессам | `IncludeTargetProcessTree` (чекбокс в UI) |
| Первые секунды после старта — шквал ложных событий (фон не сошёлся) | Прогрев `WarmupSec=2`: онсеты подавлены, фон сходится с быстрым τ=0.25 c (найдено при отладке) |
| Указатель «уползает» в центр в паузах события | Азимут замирает, когда сигнал ниже порога затухания (найдено при отладке) |
| HRTF/Atmos-миксы | Профили калибровки (M3), рекомендация стерео в доках |
| Голосовой чат внутри игры даёт ложные события | Фильтр по частотному профилю (речь 300–3.4 кГц, узкая) — M2+ |
| Античит | См. §9; технически мы — OBS-эквивалент, риск минимален, но не нулевой |

## 9. Античит и этика

- Нет инъекций, нет чтения памяти, нет симуляции ввода, нет скрытности — только публичные
  аудио-API ОС (та же поверхность, что у OBS/Discord).
- Инструмент передаёт то, что игрок с нормальным слухом слышит и так — это выравнивание
  доступности, а не преимущество сверх нормы.
- Честные оговорки для пользователей: EULA отдельных игр может запрещать любые оверлеи; в
  турнирах правила свои. Перед использованием в конкретной игре — проверять её правила;
  решение за пользователем.

## 10. Дорожная карта

- **M0 — spike: поглощён M1** — process loopback реализован сразу на NAudio 3.3.0; проверить
  активацию на сборке ОС пользователя (26300, см. риск 25H2).
- **M1 — MVP: реализован (2026-10-31), затем расширен до 360°.** Захват (процесс 8/2 каналов с
  автофолбэком, устройство) + пикер процессов + многоканальный DSP-конвейер (stereo ILD ±90° /
  5.1-7.1 вектор ±180°) + радар-круг в UI с авто-режимом 180°/360° + Emitter +
  19 юнит-тестов (пан→угол, зад/бок/фронт 7.1, слияние событий, трекер фона).
- **M2:** оверлей: **два пресета** (ComboBox): «Дуги» (секторы с рисками и меткой точного
  азимута) и «Кромка (градиент)» (свечение вдоль краёв экрана — прозрачно к центру, плотно
  к краю, сегментированный градиент, минимально отвлекающий). **Режимы цвета:** по близости
  (зеленоватый — дальше, красный/тёмно-красный — очень близко), по громкости, постоянный
  оттенок (палитра). Скрытие центральных секторов (свои звуки игрока). **Глобальный хоткей**
  вкл/выкл оверлея (RegisterHotKey, биндинг настраивается кликом по полю, работает поверх
  игры). Прозрачное topmost-окно click-through только на основном мониторе; подтверждено
  поверх реального DayZ в borderless. Демо-режим `--overlay-demo`. Тест-окно адаптивно
  (ScrollViewer, MinWidth колонок, MinSize окна). Исправлен баг: возобновлённое (склеенное)
  событие не сбрасывало EndedUtc — оверлей не показывал новую позицию, пока гасла старая дуга.
  Тонкая настройка оверлея (слайдеры): непрозрачность, размер свечения от края, ширина
  реакции, скорость затухания; **скрытые зоны** — пользователь отмечает галочками зоны,
  которые не показывать (0 = перед); пресет «Дуги» очищен от прод-меток (риски/ПЕРЕД/ЗАД
  убраны), сглаживание азимута отрисовки. Кнопки сброса настроек оверлея и детектора.
  Далее: приглушение вместо скрытия центральных зон, классификация звуков в подписях
  маркеров, трей.
- **M3 (начато — калибровка по DayZ):** по датасету выстрелов AK-74/CZ-550 с известных позиций
  (2026-10-31) построен профиль `AnalyzerOptions.DayZ()`: калибровочная кривая ILD→угол
  (пан DayZ жёсткий: диагональ ±45° ≈ 6 дБ, борт ±90° → ILD десятки дБ), направление
  якорится к пику события (усреднение top-блоков в пределах 3 дБ от пика — выстрел слоистый:
  панорамированный ствол + центрированный щелчок пули + реверб), буст вч-полос для щелчков.
  Реплей-инструмент `SoundRadar.Replay` (WAV + манифест → отчёт ошибок). Результат: макс.
  ошибка угла 5.7°, средняя ~2.1° на 10 контрольных выстрелах. Попутно исправлены
  архитектурные баги: тайминги событий по аудио-времени (не настенным часам), дедлок
  холодного старта (фон у планки + заморозка), конец события по «тишине в N полосах».
  Далее: классификация звуков по BandSalienceDb, мульти-источность, упаковка.
